# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Yarn 4 workspaces monorepo orchestrated by Turborepo (Node version in `.nvmrc`):

- `package/` — the published `react-native-spotlight-tour` library (source in `src/`, tests in `test/`).
- `example/` — React Native example app (iOS, Android and web via `metro.config.web.cjs`) that consumes the library.
- `docs/` — GitHub Pages site; API reference is generated by TypeDoc from `package/`.

## Commands

Run from the repo root unless noted:

- `yarn install` — install all workspaces
- `yarn build` — build the library (`tsc -p tsconfig.prod.json` → `package/dist/`)
- `yarn compile` — type-check all workspaces
- `yarn lint` — ESLint over the whole repo (flat config in `eslint.config.mjs`)
- `yarn test` — run tests via Turbo (Vitest, in watch mode when run directly)
- `yarn check` — compile + tests (single run) + lint; mirrors CI (`compile`, `lint`, `test:ci` on Node 22 and 24)
- `yarn docs` — generate TypeDoc API docs

Running a single test (from `package/`):

```sh
yarn test --run test/integration/main.test.tsx
yarn test --run -t "shows the overlay view"
```

The `--no-experimental-detect-module` Node flag is required for tests; the package `test` script already sets it, so prefer `yarn test` over calling `vitest` directly.

### Example app

- Start Metro from the root with `yarn start` (Turbo builds the library first), so library source changes hot-reload in the app.
- `yarn android` / `yarn ios` from the root (or inside `example/`). iOS first needs `bundle install` and `cd ios && pod install` inside `example/`.
- Web: inside `example/`, `yarn web:build` then `yarn web:start`.

## Architecture

The public API is entirely re-exported from `package/src/main.ts` (it also re-exports Floating UI middleware such as `flip`, `offset`, `shift`). `package.json` points the `react-native` field at `src/main.ts`, so RN consumers use source while others use `dist/`.

How the pieces fit together:

- **`SpotlightTour.context.ts`** — all public types (`TourStep`, `SpotlightTour`, `TooltipProps`, `Motion`, `Shape`, …), the internal `SpotlightTourCtx` (adds `spot`, `steps`, `changeSpot`), and `useSpotlightTour()`, which exposes only the public subset.
- **`SpotlightTour.provider.tsx`** — owns tour state (`current` step index, `spot` layout rect, `pausedAt`) and derives `status` (`idle`/`running`/`paused`). Moving to a step (`renderStep`) awaits both the overlay's `hideTooltip()` animation and the step's `before()` hook before setting `current`. The provider exposes the same API through context and through a ref (`useImperativeHandle`), and renders `TourOverlay` as a sibling of the children.
- **`AttachStep`** — wraps a target element in a measurable `View`. When `current` matches its `index` (number or array), it calls `measureInWindow` and pushes the rect to the provider via `changeSpot`. This is the only way the spotlight learns where to go.
- **`TourOverlay`** — renders a `Modal` with an SVG mask (`react-native-svg`) cutting out the spot using `CircleShape`/`RectShape` (geometry helpers in `helpers/shape.ts`), animates per `Motion`, and positions the step's `render()` tooltip with `@floating-ui/react-native`. Per-step options (`shape`, `motion`, `onBackdropPress`, `arrow`/`flip`/`offset`/`placement`/`shift`) override the provider-level defaults here.
- **`TourBox`** — optional prebuilt tooltip component users can return from a step's `render`.

## Testing

- Vitest with a custom environment (`package/test/environment.ts`) that registers `react-native-testing-mocks` — it replaces the upstream Vitest environment, which doesn't work with Vitest 4.
- Assertions use `@assertive-ts/core` (`expect(x).toBeNull()` style) with the Sinon plugin; stubs/spies use Sinon, reset globally in `test/setup.ts`.
- Components are tested with `@testing-library/react-native`. Native layout measurement is faked with `mockNative(...)` / `restoreNativeMocks` and data in `test/helpers/measures.ts`; `test/helpers/TestTour.tsx` provides a reusable test screen.

## Conventions

- Releases are automated with semantic-release on `main` (`package/.releaserc.json`), so commit messages must follow Conventional Commits (`feat:`, `fix:`, `chore(deps):`, …). The package version in `package.json` stays `0.0.0`.
- ESLint enforces stylistic rules (double quotes, semicolons, 1tbs), naturally sorted object keys, interface members and union/intersection types (perfectionist), and JSDoc formatting. Public props/types are documented with JSDoc including `@default` tags, which feed the TypeDoc API reference — keep them in sync when changing defaults.
- New user-facing features should also be documented in `README.md` (per `docs/CONTRIBUTING.md`).
